# RustVideoAnalyticsServer

Для читателя без опыта Rust подготовлено отдельное подробное учебное описание:
[структура сервера, модель владения, потоки и сравнение с Clang/C++](docs/RustServerTutorial.md).
PDF-снимок для чтения и печати (не пересобирается автоматически;
актуальные уточнения находятся в Markdown-учебнике):
[RustVideoAnalyticsServer-Tutorial.pdf](output/pdf/RustVideoAnalyticsServer-Tutorial.pdf).

Реализация на Rust того же REST-контракта `/api/v1/*`, что и у
`ClangVideoAnalyticsServer` и `PythonVideoAnalyticsServer`. Поэтому на него
можно направить `JsVideoAnalyticsViewer` и запускать `tests/rest_contract.py` из
Clang-проекта. Построен на `axum` / `tokio` (сегодня это стандартный выбор для
REST-сервисов на Rust) и `sqlx` для PostgreSQL.

Проект образовательный: каждый исходный файл подробно прокомментирован по-русски
в стиле C++-оригинала (шаги, объяснение «почему», пояснения по особенностям Rust:
владение, `Arc`, `Mutex`, `Condvar`, потоки).

## Что сделано

Работает по-настоящему, без OpenCV: REST, авторизация и конфигурация; захват
RTSP и файлов; детекция движения и трекинг; полнокадровый YOLO и
Tracking-YOLO-256; HLS; запись MP4; история в PostgreSQL; JPEG-превью и превью
входа YOLO; оверлей (рамки, подписи, области); управление PTZ по ONVIF.

Собрано и проверено на Rust 1.98.1: сначала на синтетическом файле
`ffmpeg testsrc`, затем **на настоящей камере** (RTSP, 2304×1296) с настоящей
моделью `yolo11n.onnx` и ONNX Runtime 1.23.2, который скачивает Clang-сервер, и
на **той же настоящей базе PostgreSQL**, которой пользуются Clang- и Python-серверы
(работающий Docker-контейнер, а не тестовая база). Подробности проверок — в
описании каждой подсистемы ниже.

## Возможности

- **REST.** Полная таблица маршрутов `server.cpp` — те же пути, методы, коды
  состояния и проверки ролей admin/viewer (`src/server.rs`).
- **Авторизация.** Bearer-сессии и PBKDF2-HMAC-SHA256 (`src/authentication.rs`);
  читает и пишет `auth.json` в том же формате, что Clang-сервер, включая
  создание администратора при первом запуске со случайным паролем в журнале.
- **Настройки.** CRUD камер в `settings.json`, сохранение конфигурации
  Motion/Tracking и YOLO, загрузка ONNX-модели с хранением по SHA-256
  (`src/runtime_state.rs`).
- **Диагностика.** Контракт метрик из 34 счётчиков, длительностей и датчиков
  (`GET /api/v1/diagnostics/profiling`, `src/profiler.rs`). Формат ответа
  совместим с C++; конвейер заполняет времена стадий, счётчики и gauges.
  Помимо 34 обязательных счётчиков возможны дополнительные ключи,
  например `pipeline.watchdogRestarts` после перезапуска watchdog.

### Захват, Motion и трекинг

`src/ffmpeg_io.rs` запускает внешний `ffmpeg` (`-f rawvideo -pix_fmt bgr24`) и
читает кадры из его stdout — так же, как HLS- и MP4-кодировщики работают в
обратную сторону. Размер кадра берётся из служебной строки stderr самого ffmpeg
(в Windows-поставке лишь один `ffmpeg.exe`, без `ffprobe`).

RTSP-вход запускается с `-timeout 5000000` (5 с в микросекундах — порт
`cv::CAP_PROP_READ_TIMEOUT_MSEC = 5000` из `video_pipeline.cpp` C++-сервера).
Без этой опции таймаута нет вовсе: при тихом обрыве связи с камерой (сеть
уронила TCP-соединение без FIN/RST — обычное дело для IP-камер, не редкость и
не поломка конкретной камеры) чтение из сокета зависает НАВСЕГДА — ffmpeg не
пишет и не завершается. Поток захвата блокируется в `read_frame()`, а
координатор и HLS-кодировщик продолжают исправно повторять последний
полученный кадр (см. «Буфер плеера HLS» и «Ограничение приоритета YOLO») —
внешне это выглядит как раз тем самым «вечным» зависанием видео у зрителя:
`captureFps` в `GET /api/v1/stream/status` застывает побитово на одном и том
же числе (проверено: 9–12 с без единого изменения), а `renderFps` при этом
остаётся здоровым — конвейер не потерял ни кадра, потому что кадров с камеры
объективно больше нет. Ни увеличение буфера плеера, ни приоритет ffmpeg
(обе меры выше) эту причину не устраняют — дело не во времени и не в CPU,
а в отсутствии таймаута на чтение сокета. (`-rw_timeout` — похожая по смыслу
опция у некоторых протоколов вроде http/tcp — на входе RTSP в этой сборке
ffmpeg не принимается вовсе, падает с «Option not found»; проверено прямым
запуском.) С таймаутом ffmpeg возвращает ошибку через 5 с молчания, внешний
цикл `capture_thread` это видит и переподключается через 3–5 с — как и было
задумано с самого начала.
`src/motion_tracker.rs` — чистая геометрия: сопоставление по ближайшему центру,
счётчики подтверждений и пропусков, сглаживание рамок, траектория.

**Детектор Motion** (`src/motion_detector.rs`) — пошаговый порт
`motion_detector.cpp`:

1. билинейное уменьшение до `frameWidth` (`max(64, ·)`, кадр никогда не
   увеличивается; выборка как у `cv::resize` с `INTER_LINEAR`);
2. перевод в серый по целочисленным весам OpenCV и размытие Гаусса 5×5
   (`[1 4 6 4 1]`, целочисленная арифметика, отражение на границах);
3. `|a − b| > brightnessThreshold` (строгое сравнение, порог 1..255);
4. `MORPH_OPEN` 3×3, `MORPH_CLOSE` нечётным ядром
   `morphologyCloseWidth × morphologyCloseHeight` (1..255), две дилатации 3×3;
5. маска областей `regions` (полигоны накладываются на маску движения);
6. внешние контуры `RETR_EXTERNAL` (пятно внутри «дырки» другого не
   сообщается), фильтр `minimumArea` по площади *ограничивающего
   прямоугольника*, возврат к координатам кадра делением с усечением.

Resize совмещён с grayscale, использует фиксированные веса (11 бит на ось)
и кеш координат. AVX2 ускоряет resize и blur, крупный resize распределяется
по постоянному пулу Rayon до четырёх потоков. При отсутствии AVX2 работает
скалярный путь. Кадры и рабочие буферы переиспользуются, чтобы убрать копии
изображений и повторное выделение памяти.

Морфология работает двумя битовыми буферами `u64`: горизонтальное окно
строится сдвигами за логарифмическое число шагов по радиусу, вертикальное —
объединением слов соседних строк. BMI2 ускоряет упаковку/распаковку при наличии
поддержки. Префиксные суммы остались только в байтовом тестовом эталоне;
стоимость ядер разных размеров не объявляется одинаковой. За границей
используются нейтральные значения. Компоненты ищутся scanline-обходом интервалов.

Побитовое совпадение всего конвейера с OpenCV не гарантируется. Опциональный
тест сравнивает маску и рамки: на тестовом кадре 94/36864 отличающихся пикселя
(0,255%) и две рамки в допуске до 2 px. Это результат конкретного теста,
а не верхняя граница ошибки для произвольного видео.

Проверки (`cargo test --release motion_detector`) — строгий порог, удаление
одиночного шума, склейка близких блобов ядром закрытия, кадры больше
`frameWidth`, области, правило площади прямоугольника, эрозия у границы, значения
размытия, пятна в «дырках», совпадение SIMD со скалярным эталоном и все
65536 масок 4×4. Ручной `benchmark_component_variants` чередует два scanline
на одинаковых синтетических масках, отдельно от видеоконвейера.
В прежней проверке на камере детектор дал `motionFps` ≈ 14,3 и нашёл
реальные движущиеся машины с траекториями. Прежние `captureFps` ≈ 28,6 были
результатом удвоения входных 15 FPS до заявленного камерой `28.58 tbr`.

### Полнокадровый YOLO

`src/object_detector.rs` — порт `object_detector.cpp`: letterbox (масштаб с
сохранением пропорций и серые поля), необязательная маска областей, инференс
через крейт `ort`, отдельные пороги уверенности (`personConfidence` для класса
0), фильтр по областям (по центру рамки) и ручной жадный NMS по классам
(замена `cv::dnn::NMSBoxes`). `detect` принимает обычный `RgbImage`, поэтому
один и тот же детектор обслуживает и полный кадр, и вырезку Tracking-YOLO-256.
`ort` загружает *внешнюю* библиотеку `onnxruntime` при старте
(`ONNXRUNTIME_DYLIB_PATH`, режим `load-dynamic`), а не линкует свою: работа идёт
с той же сборкой ONNX Runtime 1.23.2, что скачивает `build-windows.ps1` Clang-сервера.

На камере рамки YOLO точно легли на припаркованные машины.

### Tracking-YOLO-256

Отдельный поток со *второй*, независимой сессией ONNX. В каждом цикле со свежим
результатом Motion координатор предлагает ему все подтверждённые, сейчас
сопоставленные треки (`misses == 0`). Worker (`detect_tracking_objects`, порт
`detectTrackingObjects`) вырезает квадрат 256×256 вокруг трека, маскирует его до
области Motion, в которую попадает трек, запускает YOLO с `inputSize` 256 и
оставляет одну детекцию внутри оценочной области трека (ближайший центр, затем
перекрытие, затем уверенность; площадь не больше 3×). У его слота нет флага
занятости: свежая пачка заменяет ожидающую (`WorkerSlot::submit`).

Результаты попадают в `history_writer.rs`: детекция сопоставляется с
геометрической «личностью» (та же метка, IoU ≥ 0,35 или близкая рамка), две
строки Motion одного объекта сливаются в одну (`mergeTrackingEvents`), и только
при росте уверенности переписываются `object` (`car — 74%`), `yoloId` и фото
(`updateTrackingRecognition`); строка, закрытая без распознавания, получает `—`.

Проверка на камере и реальной PostgreSQL: строки вида `car — 55%` и `car — 74%`
с `yoloId`, нераспознанные закрываются как `—`, после `DELETE /api/v1/stream` не
остаётся открытых строк. Слияние двух ID Motion в одну строку на реальных данных
отдельно не наблюдалось.

### Потоки конвейера

На каждый открытый источник запускается шесть основных потоков (`src/video_pipeline.rs`),
как в C++:

- **capture** владеет `ffmpeg`, только читает и публикует новейший кадр в
  однослотовый «почтовый ящик» (`SharedCapture`): непотреблённый кадр
  заменяется, а не ставится в очередь;
- **Motion/Tracking**, **YOLO** и **Tracking-YOLO-256** владеют своими
  детекторами; `src/worker_slot.rs` (`WorkerSlot<Task, Res>`) — обобщённая форма
  слота `m_motionMutex` / `m_objectMutex` из C++. Занятый worker означает
  пропуск этого кадра, а не очередь;
- **coordinator** предлагает кадр workers, рисует то, что каждый *последним
  завершил* (возможно, по более раннему кадру: он никогда не ждёт инференса), и
  с выбранным интервалом 1/15 или 1/30 с передаёт кадр потоку показа;
- **display** — см. следующий раздел.

Кроме них работают JPEG-preview, HLS, чтение stderr FFmpeg, пул resize,
потоки ONNX Runtime и Tokio; recorder создаёт свой поток при записи.

Координатор публикует в `RuntimeState` размер кадра и три из пяти значений
FPS (`processingFps` — собственная частота координатора; `motionFps` и `yoloFps`
— частота завершённых результатов workers, 0 при выключенном режиме);
`captureFps` приходит от потока захвата, `renderFps` — от потока показа.

Остановка кооперативная: счётчик «поколения» источника увеличивается, и каждый
поток выходит при ближайшей проверке (в пределах кадра, интервала опроса в
200 мс или паузы переподключения).

### Поток показа и JPEG-превью

Порт `displayRun`: нарисованные кадры координатора попадают в ограниченный буфер
(`DisplayQueue`: не более 12 кадров, самый старый отбрасывается), а отдельный
поток ждёт стартовый запас 6 кадров и затем выдаёт кадры с выбранными 15/30 FPS
в `HlsEncoder` с темпом
`nextFrameAt = max(nextFrameAt + интервал, now)`. При паузе захвата повторяется
последний кадр, поэтому временная шкала HLS остаётся ровной независимо от
рывков анализа и RTSP.

JPEG-превью кодирует небольшой вспомогательный поток через однослотовую замену,
так что кодирование никогда не задерживает темп HLS. Кодер — крейт
`jpeg-encoder` (чистый Rust, AVX2 через функцию `simd`), качество 85,
субдискретизация 4:2:0 как у libjpeg/OpenCV. Кадр 2304×1296 кодируется за
≈ 25 мс (кодер крейта `image`: 60 мс на простое, 150–200 мс под нагрузкой
конвейера). Вторая причина медленного превью была в координаторе: кадр ставился
в очередь, только если с прошлого прошло ≥ заданного интервала, а кадры камеры идут каждые
≈ 35 мс с дрожанием, и это правило часто «перескакивало» через один-два кадра
(≈ 10 в секунду). Теперь график фиксированный
(`next = max(next + 1/FPS, now)`).

Проверка на камере при включённых Motion, трекинге и YOLO: `renderFps` держался
на 15,00 (три замера подряд); каждый сегмент HLS имеет `EXTINF:1.000000`.
Координатор больше не кодирует JPEG и HLS сам. Число *разных* кадров превью в секунду
(опрос `/api/v1/stream/frame` в течение 10 с): 8,7 → 14,2 при потолке 15
(при выключенном анализе 10,1 → 14,1).

### Ограничение приоритета YOLO

Рукописные Motion и отрисовка (без OpenCV) на тяжёлой конфигурации —
`frameWidth`/`inputSize` увеличены, области и Tracking включены — заметно
менее эффективны по CPU, чем оптимизированные реализации C++/Python-серверов.
На перегруженной машине это било не по YOLO (он и так медленный, это ожидаемо),
а по самой HLS: ffmpeg-кодировщик не получал вовремя процессорное время,
хотя наш код исправно готовил и передавал кадры по расписанию — сегмент с
`EXTINF:1.000000` реально появлялся раз в 3–5 секунд вместо одной.

Раз захват, Motion и показ вместе занимают немного ресурсов, а YOLO —
основной потребитель CPU, решение — понижать приоритет ОС-потока именно у
YOLO, а не ограничивать конвейер видео. `src/video_pipeline.rs`:
`lower_priority_for_yolo()` (крейт `thread-priority`) понижает приоритет
потоков `yolo_worker_thread` и `tracking_yolo_worker_thread` до минимального;
`raise_priority_for_pipeline()` повышает приоритет `capture_thread`,
`coordinator_thread` и `display_thread` до максимального. При перегрузке
повышенный приоритет помогает этим потокам конкурировать с пониженными;
точный темп зависит от нагрузки и блокировок ввода-вывода.
`src/object_detector.rs`: число внутренних потоков ONNX
Runtime (`CVA_ONNXRUNTIME_THREADS`) по умолчанию снижено с 2 до 1 — эти
потоки создаёт сама библиотека и они не наследуют пониженный приоритет
нашего потока-обёртки, поэтому только снижение их числа реально уменьшает
пиковую параллельную нагрузку YOLO на CPU.
`CVA_ONNXRUNTIME_CPU_ARENA` (по умолчанию `0`) управляет CPU memory arena
ONNX Runtime. Без арены крупные промежуточные буферы освобождаются между
инференсами; значение `1` возвращает её, если это потребуется другой модели.
При уровне журнала `info` сервер раз в 30 секунд пишет частоты стадий и глубину
очереди показа. На текущей модели и входе 2304 A/B после одинакового прогрева
дал 1217 → 395 МиБ Working Set и 1319 → 695 МиБ Private при неизменных
0,30 FPS YOLO. Серия из 40 замеров финальной сборки показала Working Set
140–735 МиБ, в среднем 552 МиБ: без арены память возвращается системе между
тяжёлыми инференсами, а не остаётся на пиковом уровне постоянно.
Подготовка входа также не пересчитывает геометрию неизменных регионов для
каждого пикселя каждого кадра: бинарная маска кэшируется до изменения размера
или JSON регионов. CHW-буфер около 64 МБ переиспользуется между инференсами.

Проверено на камере с тяжёлой конфигурацией (`frameWidth: 1280`,
`inputSize: 2304`, Motion/Tracking/YOLO включены, 4 региона Motion + 3 региона
YOLO): загрузка системы 100% → 85%, но, что важнее, реальный темп сегментов
HLS — с ≈ 1 сегмента в 5 секунд до ≈ 1 сегмента в секунду (21 сегмент за
20 реальных секунд), то есть настоящее реальное время вместо пятикратного
отставания. `Viewer FPS` в клиенте вырос с 1–5 до 8–13 (колеблется — тестовый
браузер запускался на той же перегруженной машине и сам конкурирует за CPU;
в отдельном браузере ожидается ближе к честным 15).

### HLS

`src/hls_encoder.rs` — порт `hls_encoder.cpp`: выделенный поток подаёт
нарисованные кадры в постоянный дочерний `ffmpeg` со строго монотонными
15 или 30 кадрами/с (повторяет последний кадр, но не «проскакивает» накопившуюся
очередь): `-c:v libx264 -preset ultrafast -tune zerolatency -crf 28`, сегменты
по 1 с (GOP всегда равен FPS, поэтому ключевой кадр приходит раз в секунду; см.
«Буфер плеера HLS» ниже про то, почему бо́льшие сегменты на самом деле
хуже, а не лучше), `-hls_list_size 6`, номера сегментов в микросекундах
эпохи (браузер никогда не смешает сегменты двух разрешений). При смене
размера кадра ffmpeg
перезапускается, а старые `.ts`/`.m3u8` удаляются — как в C++. Высота из
`hls.config` (0/480/720/1280) применяется фильтром `scale` внутри ffmpeg с
сохранением пропорций. JPEG-превью и HLS совместно читают один неизменяемый
RGB24-буфер: перед HLS больше нет полной копии кадра и перестановки каналов.
Rust передаёт исходный размер без промежуточного ресайза. Начальные значения —
720p и 30 FPS; при захвате около 14–15 уникальных FPS недостающие такты
заполняются повтором последнего кадра, поэтому временная шкала остаётся строго
30 FPS.
720p: на исходном кадре 2304×1296 это примерно в 2,6 раза снижает стоимость
декодирования в браузере и не даёт Viewer просесть до 1–3 FPS под нагрузкой
аналитики. Администратор по-прежнему может явно выбрать исходный размер, 480p
или 1280p. В отличие от C++, которая собирает строку для
`_popen`/`popen` и вручную экранирует её, здесь `ffmpeg` запускается напрямую
через `std::process::Command` с массивом аргументов — без оболочки, поэтому нет
проблем с экранированием путей с пробелами.

Буфер между координатором аналитики и потоком показа ограничен 12 кадрами и
начинает выдачу после 6 кадров (0,2 с при 30 FPS или 0,4 с при 15 FPS). Один кадр 2304×1296 занимает
8,54 МиБ, поэтому прежние 12/24 кадра удерживали 102–205 МиБ и добавляли
задержку без пользы для непрерывности: при исчерпании очереди HLS-кодировщик
сам повторяет последний кадр.

Проверка: `live.m3u8` и скользящие сегменты `.ts` отдаются по HLS-порту; сегмент,
скачанный по HTTP, декодируется `ffmpeg` без ошибок, а кадр из него — живой вид
камеры с совпадающей отметкой времени. `POST /api/v1/hls/config
{"height":720,"fps":30}` перезапускает кодировщик и даёт сегменты 1280×720
по 30 кадров. Допустимые FPS — 15 и 30; старый запрос только с `height`
сохраняет текущую частоту. После остановки источника файлы HLS остаются на
диске — так же, как в C++.

### Буфер плеера HLS

Долгое время эту проблему («постоянно колесо ожидания» у зрителя) пытались
лечить неверными средствами — история ниже сохранена намеренно, чтобы не
наступить на те же грабли снова.

**Настоящий механизм.** Viewer формально настроен на `liveSyncDurationCount:
2` в HLS.js, но эта опция здесь ничего не решает: `public/app.js` держит
свой собственный обработчик `hls.on(Hls.Events.FRAG_BUFFERED, () => {
video.currentTime = Math.max(first, last - 2); })` — при получении
**каждого** нового сегмента плеер принудительно перескакивает на ровно
2 секунды (константа в коде, не связана с `liveSyncDurationCount`) позади
края буфера. Между двумя перескоками воспроизведение идёт нормальным
темпом (1×) и «съедает» ровно `длительность сегмента` секунд из этих
фиксированных 2 с. Если сегмент близок к 2 с или больше — весь запас
съедается ПОЛНОСТЬЮ ещё до следующего перескока, и буфер регулярно
проседает почти до нуля. Поэтому:

- Первая попытка (сегменты по 1,4 с, GOP 21) не то что не помогла — она
  сделала запас МЕНЬШЕ прежнего 1-секундного: `2 − 1,4 = 0,6` с вместо
  `2 − 1 = 1` с.
- Вторая попытка заодно исправила настоящий баг метаданных: ffmpeg
  усекает `-hls_time` до целого числа секунд в поле плейлиста
  `EXT-X-TARGETDURATION` (`-hls_time 1.4` давало `EXTINF:1.400000`, но
  `EXT-X-TARGETDURATION:1` — проверено прямым запросом `live.m3u8`; это
  реальная неточность ffmpeg, стоит иметь в виду при любых будущих
  изменениях `-hls_time`). Но раз `app.js` ориентируется не на это поле, а
  на жёстко зашитые «−2 с», переход на целые 2 с (`-hls_time 2`, GOP 30)
  сделал только хуже: `2 − 2 = 0` с запаса — проверено вживую (`video.
  buffered` в браузере), margin стабильно проседал до 0,10–0,11 с перед
  каждым новым сегментом, `readyState` падал до `HAVE_CURRENT_DATA`
  (реальное заикание) в 30–40% замеров.

Правильное направление — противоположное: сегмент должен быть заметно
**меньше** 2 с, чтобы перескок к «−2 с» срабатывал чаще относительно
самого запаса и тот не успевал истощиться. Возвращены исходные,
C++-совместимые значения (`-hls_time 1`, GOP 15): запас колеблется между
2 с (сразу после перескока) и ~1 с (перед следующим сегментом) — заметно
комфортнее, чем у любых бо́льших сегментов.

**Почему `-hls_time 1` изначально тоже не спасал.** До того, как
проблема с буфером вообще всплыла, сегмент уже был равен 1 с — а колесо
ожидания всё равно появлялось постоянно. Причина была не в буфере, а в
двух независимых источниках рваного темпа продакшена сегментов, из-за
которых даже комфортный теоретический запас (~1–2 с) успевал полностью
истощаться:

1. **Приоритет ffmpeg.** `lower_priority_for_yolo()`/
   `raise_priority_for_pipeline()` поднимают приоритет ОС только *нашим*
   потокам (capture/coordinator/display) — дочерний процесс `ffmpeg`,
   кодирующий HLS, оставался с обычным приоритетом Windows и на занятой
   машине мог подолгу ждать своей очереди у планировщика, даже когда наш
   конвейер кормил его кадрами точно по расписанию (подтверждено: реальный
   темп сегментов был рваным — паузы по 4–5 с сменялись рывками, — хотя
   `renderFps`/`frameQueueSize` показывали идеальные 15 кадров/с без
   потерь). `hls_encoder.rs::spawn_ffmpeg` теперь запускает `ffmpeg` с
   флагом `ABOVE_NORMAL_PRIORITY_CLASS`
   (`std::os::windows::process::CommandExt::creation_flags`, только на
   Windows). Проверено прямым посекундным опросом `live.m3u8`:
   `EXT-X-MEDIA-SEQUENCE` растёт строго на 1 за интервал 1,39–1,49 с (19
   сегментов за 26,76 реальных секунды — среднее 1,408 с при тогдашних
   1,4-секундных сегментах) при загрузке системы 90%.
2. **Таймаут чтения RTSP.** См. «Захват, Motion и трекинг» — при тихом
   обрыве TCP-сессии с камерой захват мог зависнуть навсегда без единой
   ошибки, `captureFps` замирал побитово на много секунд, пока
   `renderFps`/HLS продолжали «честно» повторять последний кадр.
   Добавлен `-timeout 5000000` на вход RTSP.

**Как проверялось на этот раз** (после трёх неудачных попыток важно быть
дотошным): не косвенно через `curl`, а напрямую в реальном браузере —
`video.buffered`/`video.currentTime`/`video.readyState` опрашивались раз
в секунду на протяжении нескольких минут через `mcp__Claude_Browser`. На
свежем подключении с `-hls_time 1` margin держится ровно на 2,0 с не
проседая (75 замеров подряд, ни одного реального провала). Замечено
также: если вкладка браузера уходит в фон (сворачивается/теряет фокус),
Chrome троттлит её собственными средствами и это тоже выглядит как
заикание — это ограничение браузера, а не сервера, и вне досягаемости
серверных настроек.

### История в PostgreSQL

`src/history_writer.rs` — порт части `VideoPipeline::run`, отвечающей за историю,
и `finishTrackingHistories` / `finishObjectHistories`. Подтверждённый трек Motion
получает строку `tracking_history`: название области (точка в полигоне), фото —
Base64-JPEG с цветной рамкой (`historyPhoto`, `centeredSquareCrop`,
`estimatedTrackingBounds` портированы точно), координаты и `object`, который
сначала `"⏳"` или `"—"`, а затем «на месте» уточняется Tracking-YOLO-256.
Детекция полнокадрового YOLO сопоставляется с активным треком `yolo_history`
того же класса по ближайшему центру (жадно, порог расстояния зависит от размера)
или начинает новый. Обе истории закрываются (`lostAt`), когда трекер сбросил ID
или YOLO-трек не встречается дольше `absenceTimeoutSeconds`.

Записи идут из потока-координатора через `tokio::runtime::Handle::block_on` (у
этого потока нет своей среды Tokio) и только при *переходах* состояния, а не на
каждом кадре. `src/history.rs` использует лениво подключаемый пул: сервер
стартует и без доступной базы (`connect_lazy`). Ожидание SQL-запроса всё же
может задержать координатор: ленивое подключение не делает запись неблокирующей.

Проверка на реальной, давно работающей базе `qtvideoanalytics`: после
короткого прогона на камере в `tracking_history` и `yolo_history` появились
настоящие строки с UUID `event_key`, заполненным `photo` (Base64-JPEG; одну
декодировали и убедились, что на ней настоящая машина с цветной рамкой), верными
`region`, `label`, `confidence` и координатами, и смесь открытых строк и строк с
заполненным `lost_at` — то есть работают и создание, и закрытие. `DELETE
/api/v1/stream` закрыл все ещё открытые строки (число `lost_at IS NULL` стало 0).

### Запись MP4

`src/stream_recorder.rs` — порт `stream_recorder.cpp`. Сырые BGR-кадры потока
захвата кладутся в однослотовый «почтовый ящик», а выделенный поток записи по
stdin подаёт их постоянному дочернему `ffmpeg`
(`-use_wallclock_as_timestamps 1 -fps_mode vfr`, `-t {segmentMinutes*60}` для
самостоятельно сменяемых сегментов, `-movflags +faststart`). Файлы пишутся в
`RECORDINGS_PATH` под именем `YYYY-MM-DD_HH-MM-SS_{streamName}.mp4` (при
совпадении добавляется числовой суффикс). Имя потока даёт
`RuntimeState::recording_stream_name()`: `camera_{id}` для выбранной настроенной
камеры, если открытый источник точно ей соответствует, иначе `"camera"` — как в C++.

Ротации по времени таймер не нужен: `ffmpeg` завершается сам по `-t`, что для
потока записи выглядит как обычная ошибка записи в stdin, после которой он
начинает следующий сегмент. `start` / `requestStop` / `stop` / `status`
повторяют двухфазную остановку C++ (`active` и `stopping` сообщаются отдельно,
поэтому клиент опрашивает чистое завершение, а не блокируется).

Проверка на камере: `POST /api/v1/recording {"enabled":true,"segmentMinutes":10}`
создал растущий файл `2026-09-25_13-16-47_camera_1.mp4` (суффикс `camera_1`
подтверждает, что выбранная камера сопоставилась верно); `{"enabled":false}`
вернул `{"active":true,"stopping":true}`, а через секунду статус стал
`{"active":false,"currentFile":""}`. Готовый файл — настоящий 21,3-секундный
H.264 MP4 в нативном 2304×1296, 11 143 485 байт — декодируется без единой ошибки
(`ffmpeg -v error -i ... -f null -`), а кадр из середины — живой вид камеры с
совпадающей отметкой времени.

### PTZ (ONVIF)

`src/ptz_controller.rs` — порт `ptz_controller.cpp`: SOAP `ContinuousMove`
(скорости pan/tilt ограничены REST-обработчиком до [-1, 1]) или `Stop` методом POST
на `http://{stream.host}:8899/onvif/PTZ`, профиль `Profile_0`, таймаут 1500 мс,
Digest с запасным Basic. Вместо libcurl запускается системный `curl`
(без оболочки), а адрес и учётные данные передаются ему через stdin
(`--config -`), чтобы пароль не попадал в командную строку; `curl` должен быть в
`PATH` (в Windows 10+ он есть). Как и в C++, читаются *устаревшие* ключи
`stream.host/user/password`, а не выбранная камера из `stream.cameras`
(настройки только со списком `cameras` дадут 503 «camera settings are
unavailable»), и ошибкой считается только сбой транспорта.

Проверка: на локальном «ONVIF-сервере» (реальную камеру не двигали) прошёл Digest
с верным логином, тела SOAP совпали с C++ побайтно (включая формат
`x="0.500000"`), выход `tilt` за диапазон ограничен до −1, неизвестное действие
дало 400, а недоступная камера — 503.

### Превью входа YOLO

`POST` / `GET /api/v1/detection/objects/input` — двухфазный обмен, как в C++:
`POST` ставит флаг запроса и очищает сохранённый JPEG; следующий проход
полнокадрового YOLO сохраняет вход сети (`ObjectDetector::set_want_preview` /
`take_preview`: после маски областей и letterbox, до нормализации); координатор
кодирует его в JPEG качества 85 и сохраняет, сбросив флаг; `GET` отвечает 404 до
этого момента. Проход по запросу выполняется и при выключенном отображении YOLO
(он не влияет ни на рисование, ни на историю).

Проверка на камере с загруженной моделью и выключенным YOLO: 404 → `requested` →
200 примерно через 3 с (`yoloFps` остался 0); JPEG — квадрат 2304×2304 с кадром
2304×1296 по центру и серыми (114) полями.

### Оверлей на кадре

`src/overlay.rs` заменяет вызовы `cv::rectangle`, `cv::line`, `cv::polylines` и
`cv::putText`. Координатор рисует в порядке C++:

- рамки Motion или треки (рамка 2 px, подпись у левого верхнего угла — `ID 12`,
  затем ` YOLO 19` после сопоставления «личности» Tracking-YOLO-256, затем
  распознанная метка — и траектория 1 px при `tracking.trajectory`);
- области Motion (`tracking.showRegions`, жёлтые, 2 px);
- только пока работает YOLO: области YOLO (`showRegions`, синие, 1 px; область
  `selectedRegionIndex` — 2 px) и каждая детекция рамкой 1 px с подписью
  `метка NN%` на семь пикселей выше.

Названия (или описания) областей пишутся над первой вершиной. Линии и полигоны
сглажены по покрытию пикселей. Текст — растровые шрифты крейта
`embedded-graphics`; для не-ASCII текста используется вариант ISO 8859-5, поэтому
русские названия областей отображаются (OpenCV печатает вместо них `?`). Толщина
рамок совпадает с C++ (2 px у Motion, Tracking и фото истории).

Проверка: юнит-тесты (толщина и обрезка рамок, концы линий, сглаженные края,
базовая линия текста, кириллица, обрезка) и живая камера с двумя областями с
русскими названиями и движущимися треками: `ID 12 YOLO 19 car`,
`ID 22 YOLO 20 person`, метки `car 58%` и траектория нарисованы и читаются на кадре
2304×1296.

## Без OpenCV

Крейт `image` используется только для типов буферов (`RgbImage`), `imageops`
(фото истории, letterbox) и кодирования маленьких фото истории 256×256; JPEG
превью кодирует `jpeg-encoder`. Всё остальное «компьютерно-зрительное» —
детекция движения, морфология, контуры, рисование — написано вручную, чтобы не
подключать ещё один крейт с CV-зависимостями и оставить набор зависимостей
небольшим.

## Известные ограничения

Исторические проверки на камере и приведённые выше значения FPS относятся
к конкретным прогонам и оборудованию; это не гарантии для текущей конфигурации.

- Профайлер (`GET /api/v1/diagnostics/profiling`) хранит последние 2048
  длительностей каждого этапа, 34 счётчика прохождения кадров, gauges и память
  процесса. Сброс накопленных значений выполняется `DELETE` того же маршрута.
  `count` и `meanMs` относятся ко всему периоду с запуска/сброса;
  `p50/p95/p99` и `maxMs` — к окну последних 2048 замеров.
- Текст оверлея рисуется растровыми шрифтами 9×15, а не штриховыми шрифтами
  Hershey из OpenCV: форма букв отличается от C++ (размер и позиция совпадают);
  `thickness 2` — жирный вариант.
- Рукописные циклы Motion и рисования быстры только при `cargo build --release`.
  Отладочная сборка работает корректно, но примерно в 10 раз медленнее на
  большом кадре. Инференс ONNX Runtime от профиля сборки не зависит (библиотека
  предкомпилирована).
- Остановка потоков кооперативная (счётчик поколения проверяется между кадрами и
  в опросе раз в 200 мс либо в паузе переподключения), а не синхронное
  присоединение `std::jthread`.
- Побитовое совпадение Motion с OpenCV не гарантируется; маска и рамки
  проверяются отдельным opt-in тестом с допусками.
- Слияние двух ID Motion в одну строку истории реализовано по C++, но на
  реальных данных отдельно не наблюдалось.
- Понижение приоритета YOLO (см. «Ограничение приоритета YOLO») и
  повышение приоритета ffmpeg-кодировщика HLS (см. «Буфер плеера HLS») —
  не замена настоящей оптимизации, а перераспределение приоритетов ОС.
  На тяжёлой конфигурации при полностью загруженной системе это
  возвращает HLS к реальному времени, но не снижает саму нагрузку: система
  всё ещё занята заметно (в тестах — 85–90%), и посторонний процесс на той
  же машине с ещё более высоким приоритетом может забрать своё и снова
  просесть по кадрам — приоритеты ОС не защищают от конкуренции с
  процессами вне этого сервера, только снижают шанс просадки от обычных
  фоновых процессов.

## Длительный тест

`scripts/soak-test.ps1` наблюдает уже запущенный сервер, ничего не меняя и не
перезапуская. Он пишет CSV с health, задержкой ответа, CPU/памятью Rust,
числом потоков и дескрипторов, процессами ffmpeg, возрастом плейлиста и
последнего HLS-сегмента. Переходы в сбой и восстановление пишутся отдельно.

Ночной запуск на 10 часов с замером каждые 5 секунд:

```powershell
pwsh -File scripts\soak-test.ps1 -DurationHours 10 -SampleSeconds 5
```

Встроенный watchdog сервера проверяется раз в 5 с: если после получения
кадров захват продолжает продвигаться, а координатор не продвигается 15 с,
либо захват не продвигается 60 с, создаётся новое поколение RTSP-конвейера.
Для контроля координатора последний прогресс захвата должен быть не старше
10 с. Файловый источник watchdog не перезапускает; до первого кадра эти
условия также не срабатывают. Смена поколения кооперативная и не прерывает
заблокированный системный вызов старого потока немедленно.

Результаты сохраняются в `C:\work\settings\runtime\rust\soak`. Мониторинг
намеренно не перезапускает сервер: ночной тест должен зафиксировать исходный
сбой. Это относится к скрипту наблюдения: встроенный watchdog сервера
продолжает работать и может перезапускать RTSP-конвейер.

## Сборка

Нужен Rust (stable); `ffmpeg` по пути `FFMPEG_PATH` (или платформенному по
умолчанию — см. `src/config.rs`) для захвата видео; только для YOLO —
`ONNXRUNTIME_DYLIB_PATH` с путём к `onnxruntime.dll` / `.so` (например, той же
библиотеке, которую скачивает `build-windows.ps1` Clang-сервера); для PTZ —
`curl` в `PATH`. Сервер стартует без PostgreSQL, но запросы истории могут ожидать недоступную
базу и задерживать координатор. Без модели можно работать с выключенным YOLO.

```powershell
cargo build --release
cargo test --release   # полный набор; benchmark и OpenCV-тест запускаются отдельно
```

## Запуск

Переменные окружения повторяют Clang-сервер: `SETTINGS_PATH`, `DATA_PATH`,
`CONFIGURATION_PATH`, `AUTH_PATH`, `RECORDINGS_PATH`, `SERVER_HOST`,
`SERVER_PORT` (по умолчанию 8080), `HLS_PORT` (по умолчанию 8888), `DB_HOST` /
`DB_PORT` / `DB_NAME` / `DB_USER` / `DB_PASSWORD`, `SERVICE_NAME`, `LOG_PATH`,
`QTVIDEOANALYTICS_LOGIN` / `QTVIDEOANALYTICS_PASSWORD` (для создания
администратора при первом запуске) — плюс `ONNXRUNTIME_DYLIB_PATH` (новая в этом
проекте: C++-сервер линкует ONNX Runtime при сборке, поэтому у него такой
переменной нет). Значения по умолчанию слегка различаются по платформам, как у
C++-сервера (`#[cfg(windows)]` в `src/config.rs`). Модель подхватывается так
же: положите файл `.onnx` в `DATA_PATH/models/` (или загрузите через
`POST /api/v1/detection/objects/model`) и включите через
`POST /api/v1/detection/objects/config`.

```powershell
$env:SETTINGS_PATH = "settings.json"
$env:DATA_PATH = "runtime/data"
cargo run --release
```

python tests/rest_contract.py  # из Clang-проекта: stream/status, stream/frame,
                               # запись и PTZ работают на настоящей камере или файле
