# Сравнение серверов Clang/C++, Python и Rust

Документ фиксирует результаты сопоставимого прогона трёх серверных реализаций
от 23 октября 2026 года. Это измерение производительности полного конвейера
видеоаналитики, а не сравнение языков программирования в общем случае.

## Условия измерения

| Параметр | Значение |
|---|---|
| Сценарий | `Full`: захват, Motion, Tracking, полноразмерный YOLO и YOLO сопровождаемых объектов |
| Видео | `benchmark-sumrak.mp4`, один и тот же SHA-256 для всех серверов |
| Модель | `yolo11n.onnx`, один и тот же SHA-256 для всех серверов |
| Прогрев | 120 секунд |
| Измерение | 300 секунд на сервер |
| Процессор | один компьютер, 24 логических процессора |
| OpenCV | 2 потока |
| ONNX Runtime | 2 потока |
| Запуски | последовательно, по одному серверу |

Сравнивались Clang/C++ 0.1.18, Python 0.1.6 и Rust 0.1.2. Поэтому цифры
характеризуют именно эти версии и этот стенд. Для статистически строгого вывода
нужны повторные прогоны; приведённые значения следует воспринимать как
инженерный снимок производительности.

## Общий результат

| Сервер | Обработка, FPS ↑ | CPU, экв. ядер ↓ | CPU машины ↓ | Макс. working set, MiB ↓ |
|---|---:|---:|---:|---:|
| Clang/C++ | 12,70 | 4,15 | 17,29% | 1 528,81 |
| Python | 12,61 | 3,69 | 15,39% | 1 625,02 |
| Rust | **14,23** | **3,21** | **13,36%** | **1 231,86** |

В этом прогоне Rust обработал больше кадров при меньшей суммарной загрузке CPU
и меньшем максимальном working set: примерно на 12% больше FPS, чем Clang/C++,
при использовании на 23% меньшего CPU; относительно Python — на 13% больше FPS
при использовании на 13% меньшего CPU. Памяти Rust потребовалось примерно на
19% меньше, чем Clang/C++, и на 24% меньше, чем Python.

Однако это не означает, что Rust быстрее на каждом этапе. Итоговый FPS отражает
работу всего асинхронного конвейера с очередями глубиной один: занятый YOLO-worker
может пропустить новый кадр, не останавливая Motion, Tracking и публикацию
последнего готового результата.

## Задержки этапов

Средние значения в миллисекундах; меньше — лучше.

| Сервер | Чтение кадра | Motion | Tracking |
|---|---:|---:|---:|
| Clang/C++ | 7,72 | **5,57** | 0,0071 |
| Python | 9,09 | 12,36 | 0,1012 |
| Rust | **5,78** | 26,75 | **0,0045** |

- Clang/C++ показал лучший Motion: примерно в 2,2 раза быстрее Python и в
  4,8 раза быстрее Rust. Это результат конкретных реализаций алгоритма,
  операций с изображениями и распределения работы между потоками, а не
  универсальное свойство C++.
- Rust быстрее читал кадры и имел минимальную задержку Tracking. Tracking в
  Rust был примерно в 1,6 раза быстрее Clang/C++ и в 22 раза быстрее Python,
  но абсолютные значения Clang/C++ и Rust в обоих случаях намного меньше 1 мс.
- Python отстал на коротких CPU-этапах, где заметнее накладные расходы объектов
  и координации, но основная тяжёлая работа OpenCV и ONNX Runtime всё равно
  выполнялась нативными библиотеками.

## YOLO

| Сервер | Full 2304 mean / p95, мс ↓ | Завершено Full 2304 | Tracking 256 mean / p95, мс ↓ | Завершено Tracking 256 |
|---|---:|---:|---:|---:|
| Clang/C++ | **1 052,69 / 1 197,75** | **273** | **18,64 / 35,85** | 941 |
| Python | 1 109,24 / **1 173,09** | 262 | 24,12 / 41,59 | 903 |
| Rust | 1 633,65 / 1 731,45 | 180 | 22,39 / 36,19 | **1 056** |

Clang/C++ дал наименьшую среднюю задержку обоих вариантов YOLO. Для
полноразмерного входа он был примерно на 5% быстрее Python и на 36% быстрее
Rust. Python имел немного лучший p95 полноразмерного YOLO, чем Clang/C++, при
чуть большей средней задержке; это показывает, что одного среднего значения
недостаточно для оценки стабильности.

Rust завершил меньше полноразмерных инференсов, хотя показал лучший общий FPS.
Причина — независимое планирование: медленный Full YOLO чаще оставался занят,
новые предложения кадров пропускались, а остальные этапы продолжали работу.
Одновременно Rust завершил больше задач Tracking YOLO, поскольку число таких
задач зависит от обнаруженных и сопровождаемых объектов, а не только от FPS.
Поэтому количество инференсов нельзя использовать как прямую меру точности или
как полностью одинаковую нагрузку между реализациями.

## Очереди и пропуски

| Сервер | Кадров захвачено | Motion завершено | Motion пропущено как busy | Кадров заменено последним |
|---|---:|---:|---:|---:|
| Clang/C++ | 4 268 | 3 800 | 16 | 452 |
| Python | 3 716 | 3 716 | 0 | 0 |
| Rust | 4 276 | 4 276 | 0 | 0 |

У Clang/C++ часть кадров была заменена более свежими до обработки, а 16 задач
Motion не были приняты занятым worker-ом. Это предусмотренное поведение
real-time конвейера: при перегрузке важнее обработать актуальный кадр, чем
накапливать задержку. Python и Rust в этом прогоне успевали передать каждый
захваченный кадр в Motion.

## Вывод

- **Rust** дал лучший общий FPS, минимальную загрузку CPU и минимальный расход
  памяти, но его полноразмерный YOLO был самым медленным.
- **Clang/C++** был лучшим на Motion и по средней задержке YOLO, ценой большей
  загрузки CPU и более агрессивного отбрасывания устаревающих кадров.
- **Python** оказался близок к Clang/C++ по общему FPS и Full YOLO, но использовал
  больше памяти и уступил на коротких Motion/Tracking-этапах.

Практический выбор зависит от приоритета. Для ресурсоэффективного основного
конвейера этот прогон говорит в пользу Rust; для минимальной задержки Motion и
YOLO — в пользу Clang/C++; Python остаётся конкурентоспособным вариантом для
быстрой разработки и изменения аналитической логики. Перед эксплуатационным
решением сравнение следует повторить на целевом оборудовании, с нужным RTSP-
потоком, моделью и настройками областей.

## Что тест не доказывает

Прогон не измеряет точность детекции, качество Tracking, задержку HLS от камеры
до браузера, пропускную способность REST API, время запуска, размер сборки и
поведение при длительной работе. Он также не отделяет влияние языка от влияния
архитектуры и конкретной реализации алгоритмов.
